# Product Audience Frontend Audit

## 1. Current Product Data Structure

Product mock data lives in `app.js` in the `products` array (`app.js:879`). Each product currently includes core catalog and dashboard fields:

- `id`, `name`, `tower`, `tribe`, `category`, `description`
- `lastActivity`, `discoveryCount`, `doneCount`, `progressCount`, `favorite`
- `about`, `metrics`, `squad`, `participants`, `start`, `end`, `artifacts`
- optional product-level `personas`
- optional product-level `stakeholders`

`Cora Promocoes` defines product personas at `app.js:899` and stakeholders at `app.js:933`. `Cora Precos` defines personas at `app.js:1011` and stakeholders at `app.js:1045`.

Persona shape:

```js
{
  id,
  name,
  type,
  description,
  goals,
  pains
}
```

Stakeholder shape:

```js
{
  id,
  name,
  area,
  role,
  description,
  interest
}
```

Products without explicit audience arrays are enriched at runtime by default builders and accessors:

- `getProductPersonas(product)` (`app.js:2049`)
- `getProductStakeholders(product)` (`app.js:2055`)

The product detail page structure is static in `index.html:362`. It renders hero, metrics, user/team info, timeline-like stakeholder card, artifacts, and discovery list. It does not currently render product-level personas or product-level stakeholder catalogs.

## 2. Current Discovery Data Structure

The base mock discovery is `discoveryTemplate` (`app.js:1308`). It contains:

- identity and status: `id`, `name`, `status`, `variant`
- discovery content: `problem`, `objective`, `insights`, `csd`, `tags`, `artifacts`, `methods`, `evidence`
- selected audience references: `selectedPersonaIds`, `selectedStakeholderIds`
- display snapshots: `selectedPersonas`, `selectedStakeholders`

Draft discoveries created from the wizard start from `createBlankDraftDiscovery()` (`app.js:1457`) and include empty selected audience arrays by default (`app.js:1479`).

Created discoveries are persisted through `upsertCreatedDiscovery()` (`app.js:567`). That function normalizes methodology and selected audience before saving (`app.js:572`).

New discovery creation saves audience selections in both legacy and MVP draft paths:

- legacy/CrewAI path: `createNewDiscoveryDraft()` (`app.js:7551`), saving audience fields at `app.js:7605`
- MVP backend path: `createMvpDiscoveryDraft()` (`app.js:7625`), saving audience fields at `app.js:7670`

Discovery IDs remain the source of truth for selected product audience. Snapshots exist for display stability if product mock data changes or is unavailable.

## 3. Where Personas And Stakeholders Are Currently Defined

There are two separate concepts in the code today:

1. Product-level personas/stakeholders:
   - product `personas` arrays on product objects (`app.js:899`, `app.js:1011`)
   - product `stakeholders` arrays on product objects (`app.js:933`, `app.js:1045`)
   - fallback accessors/builders through `getProductPersonas()` and `getProductStakeholders()` (`app.js:2049`, `app.js:2055`)

2. Research participant selectors in the new discovery wizard:
   - `flowSelectOptions.personas` and `flowSelectOptions.stakeholders` (`app.js:679`)
   - these are not product-level personas/stakeholders; they are research participant planning labels.

Discovery-level selected references are normalized with:

- `normalizeSelectedPeopleIds()` (`app.js:2061`)
- `normalizePersonaSnapshot()` (`app.js:2067`)
- `normalizeStakeholderSnapshot()` (`app.js:2087`)
- `resolveDiscoveryPersonas()` (`app.js:2115`)
- `resolveDiscoveryStakeholders()` (`app.js:2128`)
- `enrichDiscoveryPeopleSelection()` (`app.js:2157`)

## 4. Where Personas And Stakeholders Are Currently Rendered

New discovery wizard:

- Markup placeholder is in the participants step (`index.html:1047`).
- The dynamic container is `data-new-discovery-product-people` (`index.html:1054`).

Discovery detail page:

- Base layout is `index.html:501`, with main grid at `index.html:502` and methodology rail at `index.html:632`.
- Audience panel is injected dynamically by `renderDiscoveryPeoplePanel()` (`app.js:6263`) after the workflow cockpit or summary.

Product detail page:

- Product-level personas and stakeholder catalogs are not currently rendered on the product page.
- Existing product page info cards show `squad`, `participants`, `start`, and `end` (`index.html:400`), populated by `renderProductPage()` (`app.js:6347`).

## 5. Existing Routes And Hash Navigation Patterns

Routing is hash-based and centralized in `setRoute()` (`app.js:4291`).

Current route types:

- `#home`
- `#products`
- `#product/:productId`
- `#discovery/:discoveryId/:productId`
- `#synthesis/:discoveryId/:productId`
- `#interview/:methodId/:discoveryId/:productId`
- `#interview-session/:participantId/:methodId/:discoveryId/:productId`

Current route parsing helpers:

- `getCurrentProductId()` (`app.js:4190`)
- `getCurrentDiscoveryId()` (`app.js:4219`)
- `getCurrentInterviewMethodId()` (`app.js:4243`)
- `getCurrentInterviewParticipantId()` (`app.js:4257`)
- `getCurrentRoute()` (`app.js:4266`)

Route side effects:

- `setRoute()` toggles visible `[data-view]` screens (`app.js:4298`).
- It updates shell mode classes such as `product-mode`, `discovery-mode`, and `discovery-detail-mode` (`app.js:4308`).
- It calls page renderers such as `renderProductPage()` and `renderDiscoveryPage()` (`app.js:4324`, `app.js:4328`).
- Leaving discovery stops polling (`app.js:4316`).

No nested route currently exists for product persona or stakeholder CRUD.

## 6. Existing Modal Patterns

The prototype uses hidden modal backdrops and data attributes rather than a shared modal manager.

Current modal/drawer examples:

- recording modal: `data-recording-modal` (`index.html:887`)
- method entry drawer: `data-method-entry-modal` (`index.html:920`)
- new discovery full-page flow: `data-new-discovery-modal` (`index.html:964`)

Common markup patterns:

- wrapper `.modal-backdrop`
- `hidden` attribute for visibility
- `role="dialog"` and `aria-modal="true"`
- close buttons with `.modal-close`
- data attributes for JS references

Common JS patterns:

- open/close functions toggle `hidden`
- new discovery modal adds/removes `body.flow-open` (`app.js:4173`, `app.js:4180`)
- close buttons and backdrop clicks are wired directly near the bottom of `app.js`
- forms submit via `addEventListener("submit", ...)`

Form patterns:

- Native form elements with data attributes.
- Multi-step wizard forms for new discovery.
- Simulated multiselects using buttons plus dynamically appended checkbox menus.
- Selectable card buttons use `aria-pressed` for product personas/stakeholders in the discovery wizard.

## 7. LocalStorage Keys Used By Products And Discoveries

Local storage keys are declared at `app.js:517`:

- `discoveryIa.createdDiscoveries`
- `discoveryIa.productFavoritesByUser`
- `discoveryIa.localMockRuns`

Usage:

- Created discoveries are loaded by `loadCreatedDiscoveries()` (`app.js:541`) and saved by `saveCreatedDiscoveries()` (`app.js:559`).
- Product favorites are stored per user profile through `PRODUCT_FAVORITES_STORAGE_KEY` (`app.js:626`, `app.js:647`).
- Local mock workflow runs use `LOCAL_MOCK_RUNS_STORAGE_KEY` (`app.js:2816`, `app.js:2832`).

There is no current localStorage key for product-level persona/stakeholder edits. Product audience is currently mock data in `products`, with runtime fallback builders.

## 8. What Needs To Change To Support CRUD For Product Personas And Stakeholders

Data model:

- Add a product-audience persistence layer separate from created discoveries.
- Recommended key: `discoveryIa.productAudienceByProduct`.
- Store by product ID:

```js
{
  [productId]: {
    personas: [],
    stakeholders: []
  }
}
```

- Merge persisted audience over mock product audience during app load or via `getProductPersonas()` / `getProductStakeholders()`.
- Keep IDs stable. Changing an ID will break discovery selections unless aliases/migration exist.
- Continue using discovery `selectedPersonaIds` and `selectedStakeholderIds` as the source of truth.

Utilities:

- Add loaders/savers for product audience localStorage.
- Add upsert/delete helpers for product personas.
- Add upsert/delete helpers for product stakeholders.
- Add ID generation that avoids collisions inside a product.
- Add guardrails for deletion: if a persona/stakeholder is selected by any created discovery, show a warning or convert delete into archive/inactive.

Rendering:

- Add product-page sections for "Personas do produto" and "Stakeholders do produto".
- Use compact cards/lists consistent with existing dashboard cards.
- Add empty states for products using fallback data or no custom audience.
- Add action buttons for create/edit/delete.

Editing UI:

- Reuse existing modal/drawer pattern rather than introducing a framework.
- A side drawer is a better fit than full-page modal for editing one persona/stakeholder.
- Forms should use data attributes and native submit handling.
- Required fields should be minimal:
  - persona: `name`, `type`, `description`, optional `goals`, `pains`
  - stakeholder: `name`, `area`, `role`, `description`, optional `interest`

Integration points:

- New discovery wizard should automatically read updated product audience through `getProductPersonas()` and `getProductStakeholders()`.
- Discovery detail should continue resolving selected IDs against product data first and snapshots second.
- If a product persona/stakeholder is edited, existing discovery snapshots should not be overwritten automatically unless explicitly requested.

## 9. Implementation Order

1. Add product audience persistence helpers.
   - Load/save `discoveryIa.productAudienceByProduct`.
   - Merge persisted product audience with mock data.
   - Handle invalid/corrupted localStorage safely.

2. Add product audience renderers on Product Detail.
   - Render personas and stakeholders as product-owned catalogs.
   - Include empty/loading-safe states.
   - Do not touch discovery detail layout yet.

3. Add create/edit drawer UI.
   - Reuse `.modal-backdrop`, drawer, `role="dialog"`, `hidden`, and data-attribute patterns.
   - Implement one generic audience editor if possible, with `type = persona | stakeholder`.

4. Add CRUD handlers.
   - Create/update/delete product persona.
   - Create/update/delete product stakeholder.
   - Persist after every change.
   - Re-render product page and update wizard selection if modal is open.

5. Add deletion safeguards.
   - Detect selected IDs in `createdDiscoveries`.
   - Prefer archive/inactive or warn before delete.
   - Preserve snapshots in existing discoveries.

6. Validate new discovery flow.
   - Ensure updated product audience appears in the wizard.
   - Ensure selected IDs and snapshots persist in created discovery.
   - Ensure creating with no selected audience still works.

7. Regression QA discovery detail.
   - Existing mock discovery still shows selected audience.
   - New draft discovery still shows selected audience after reload.
   - Methodology rail remains right-only on desktop.
   - Mobile layout remains one column.

## 10. Risks Of Breaking The Discovery Page Layout

- The discovery detail layout is sensitive to the `new-discovery-detail` scoped CSS (`styles.css:3232`).
- The main grid uses 12 columns and explicit order/span rules (`styles.css:3246`, `styles.css:3271`).
- The methodology rail is the only visible content in `.discovery-aside`; chat and evidence panels are hidden in discovery detail scope (`styles.css:3332`).
- `renderDiscoveryPeoplePanel()` injects the audience panel after the workflow panel (`app.js:6263`). Changing the workflow DOM anchor can move the audience panel unexpectedly.
- Product CRUD should not reuse `.discovery-aside`, `.discovery-main-grid`, or `.discovery-people-panel` outside the discovery detail context.
- Avoid broad selectors like `.info-card`, `.artifacts-panel`, or `.methodology-panel` without `.discovery-page.new-discovery-detail` scope, because these classes are reused on product and discovery pages.
- Do not move `Prazo discovery` or `Equipe` into the right rail; the current acceptance rule is that the right rail belongs only to Methodology.
- If CRUD introduces new product-page cards, keep them under product-page-specific classes to avoid inheriting discovery-detail grid spans.
- Be careful with `display: contents`; it is currently used to flatten existing discovery cards into the main grid. Moving product audience cards into this area without scoped CSS can create unexpected grid placement.
- Mobile breakpoints override discovery detail layout around max-width 1024 and 760. Any new audience UI must be tested below 900px.
